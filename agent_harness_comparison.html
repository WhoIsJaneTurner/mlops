Agent harness comparison

What a harness is, which ones people actually use, how they differ from the libraries they are built on, and the new layer of tools that wrap harnesses to run them in loops, in parallel and in the cloud.

What a harness is

A model by itself only turns text into text. A harness is everything wrapped around it that lets it act: the agent loop, tool definitions (read, write, edit, shell), context management, the system prompt, permissions and the interface a person works through. One survey puts it plainly: a wrapper around an LLM that gives it tools to read and write files, run commands and iterate on code autonomously.

The vocabulary is still settling, so it helps to separate four layers. The lower two are used to build agents. The upper two are run as tools.

4 · Harness of harnesseswraps other harnesses
Loops, parallel fleets, supervisors and hosted runtimes that drive one or many harnesses as workers. Examples: ralph-orchestrator, Claude Squad, Gas Town, Claude Managed Agents.
3 · Harnessbatteries included
An opinionated, ready-to-run agent with tools, prompt and UI. Examples: Claude Code, Codex CLI, Cursor, Pi, OpenCode.
2 · Substratelibraries, frameworks, runtimes
Abstractions and infrastructure from which agents are assembled. Examples: LangChain, LangGraph, CrewAI, OpenAI Agents SDK, Google ADK.
1 · Modelthe weights
Claude, GPT, Gemini, Kimi, open-weight models. Reached through an API.
The boundary is blurry on purpose. Some products ship as a library and a harness: the Claude Agent SDK exposes the same loop Claude Code runs, and Pi is a monorepo of reusable packages with a CLI on top. The test applied here: a product counts as a harness if work can be started on a task without the loop first being written or the tools first being chosen.

Substrate libraries: what harnesses are built from

LangChain's own taxonomy is the clearest found. It splits the space into frameworks (abstractions that make building easier), runtimes (production infrastructure such as durable execution and persistence) and harnesses (opinionated, batteries-included agents built on top). Under that scheme, most of the names people call “agent frameworks” belong below the harness line.

Where harnesses actually differ

The same model can feel very different in two harnesses. A small hands-on test of Claude Code, Codex, OpenCode and Pi found large differences in speed, token use and cost per successful task on the same work, which supports a point several authors make: the harness, not just the model, decides how fast, safe and expensive the result is. The figures are illustrative, since they came from one reviewer's run.

Axis 1

Model strategy

Locked harnesses (Claude Code, Gemini CLI, Codex by default) are tuned to one vendor's models. Open ones (OpenCode, Pi, Aider, Goose) trade tuning for freedom to switch.

Axis 2

Prompt and tool surface

Pi ships four tools and a tiny published prompt. Claude Code ships ten or more tools plus sub-agents and hooks. Less surface means fewer tokens and more transparency; more means more built-in capability.

Axis 3

Safety posture

Codex leans on OS-level sandboxing (Seatbelt, seccomp). Pi runs with full system access and no prompts by default. OpenCode has no OS sandbox. The choice depends on where the agent will run.

Axis 4

Extensibility

Claude Code: skills, plugins, hooks, MCP. Pi: TypeScript extensions and packages. Codex: an embeddable App Server protocol that JetBrains and Xcode use.

Axis 5

Where it runs

Local terminal, IDE, desktop app, or a cloud VM to which work is handed. Cursor 3, Codex and Claude Code all now offer a cloud mode.

Axis 6

Embeddability

Whether it can be driven from code. Codex (SDK, exec, App Server), Claude (Agent SDK) and Pi (SDK) can; this is what makes the next layer possible.

Axis 7

Process footprint

A CLI call starts a full runtime each time. In a mock-model test, each concurrent Claude Code CLI child added about 73–94 MB of private memory, while each concurrent Pi session in a shared process added about 0.1–4 MB. See the next section.

Axis 8

Cache discipline

Where the harness places prompt-cache breakpoints and how stable it keeps the prefix. See the caching section.

Process footprint: CLI versus library

Most of the harnesses above are Node or similar runtimes wrapped as a command-line tool. Each time one is invoked as a command, a new process is started with its own runtime, loaded tool definitions, session state and any MCP servers it launches. For one person in one terminal this is invisible. For a script, a CI job, an orchestrator or a service that invokes a harness many times at once, the memory cost accumulates quickly. The question measured here was narrow: what does each additional concurrent request cost in memory when a harness runs as a subprocess, compared with when it runs as a session inside the host process?

Subprocess per request

73–94 MB of new memory per concurrent request

Claude Code CLI children, launched one per request, each added about 73 MB with a trivial reply and about 94 MB when the request had read twelve large files. The figure grows with the context a child holds.

Sessions in one process

About 0.1–4.0 MB per concurrent session

Pi sessions hosted in a single Node process grew the process from about 133 MB to 200 MB at 600 trivial concurrent requests, and to 2,510 MB at 600 requests that each read the twelve files.

Reading the numbers

Resident size misleads

Each child reported 226–251 MB resident, but most of that is one binary image shared between children. At 28 children the resident figures sum to 6.2 GB while the machine actually used 2.0 GB.

How it was measured, and why

  • A mock model. A local server that imitates the Anthropic Messages API stood in for the model. This isolates harness overhead from model behaviour, avoids credentials and paid calls, and lets every reply be held open for 30 seconds so that all N requests are provably in flight at the same moment. The mock’s own counter was required to equal N before each sample was taken, and it did at every level. One level (400 sessions with file reads) was re-run after the measurement script’s own polling request to the mock failed; the re-run completed with no errors.
  • Subprocess side. The Claude Code CLI (version 2.1.292, the binary bundled with the Claude Agent SDK) was started once per request in the way the SDK starts it, with streaming JSON over stdin and stdout, a clean environment and only the Read tool enabled. Levels ran from 1 to 28 concurrent children.
  • In-process side. The Pi coding-agent SDK (version 1.0.4) created N sessions inside one fresh Node process per level, with in-memory session storage, compaction off, no resource discovery and only the read tool, against the same mock. Levels ran from 1 to 600.
  • Two workloads. In the trivial workload the model returned one short streamed reply. In the tool workload the model first asked to read twelve text files of about 117 KB each (about 1.4 MB of tool output) and then replied, so the harness had to hold real tool results in memory.
  • Three memory readings. Resident size (RSS) counts a shared page once in every process that maps it, so it overstates the total when children share a binary. Proportional size (PSS) divides each shared page among the processes sharing it. Private anonymous memory is what one more process adds that no other process holds. System memory used (total minus available, read before and after the children started) gives an independent cross-check, and its slope against N is the marginal cost per child.
  • Environment. One Linux sandbox with 2 vCPUs and 8 GB of RAM on x86-64. One run per level; the per-child values were stable across levels, which is the evidence that the readings are not noise.

What the comparison does and does not establish. At 28 concurrent requests the subprocess approach had used 2.0 GB with trivial replies and 2.6 GB with the file reads, against 142 MB and 388 MB for 50 sessions in one process in the same two workloads. The mechanism is the difference between duplicating a runtime per request and sharing one. It says nothing about model latency, number of turns, token cost or answer quality, because the model was a mock; those need a real model and a fixed task. The in-process sessions also share fate: a crash, a memory leak or a blocked event loop in the host affects all of them, which separate processes would contain. The Pi runs used a minimal configuration, so a default product install that discovers skills, extensions and MCP servers would add to the base. One run was made per level on one machine.

Rule of thumb. The measurements point to a simple sizing rule. A subprocess harness costs its shared image once plus a private share per concurrent request, which here was roughly 70 to 95 MB and rises with the amount of tool output held. An in-process session costs a base process once plus about 0.1 MB to 4 MB per concurrent session in these workloads. Where a harness will be invoked more than a few times at once, a shared runtime is therefore advisable: a library call in the host process, a long-lived server, or a hosted service. Spawning a CLI per task is best reserved for low concurrency, with an idle timeout so that abandoned processes do not accumulate.

Prompt caching and cache breakpoints

An agent resends nearly the same prompt on every step: tool definitions, system prompt, project instructions, then a conversation that grows with each tool result. Prompt caching lets the provider reuse its work on the unchanged beginning of that prompt, so that only a fraction of the normal input price is paid for it and the wait for the first token is shorter. A cache breakpoint is a marker on a block of the prompt that says “cache everything up to and including here”. For a long-running coding agent, the difference between good and bad breakpoint placement is often the largest line in the bill.

Cached prefix, left to right. Each marker is a breakpoint; the new turn is always processed fresh.

  • Prefix order is fixed: tools, then system prompt, then messages. A change at any point invalidates everything after it. Edit one tool definition and the whole cache goes cold.
  • Up to four explicit breakpoints per request. Automatic placement can also be requested, where the breakpoint sits on the last cacheable block and moves forward as the conversation grows; that uses one of the four slots.
  • Writes only happen at breakpoints, and a lookup checks about 20 blocks back from each one. In a long agent turn with many tool calls, an old entry can fall outside that window, so long sessions need a second breakpoint further back.
  • Lifetime: five minutes by default, refreshed each time the entry is read; one hour at a higher write price. Pricing as published: writes cost 1.25× the base input price (2× for the one-hour option) and reads cost a small fraction, 0.1× on most models and lower on some.
  • Minimum size: a prefix below the model's minimum (512 tokens on the current Sonnet and Opus models, more on older and smaller ones) is silently not cached.
The classic mistake. Putting the only breakpoint on a block that contains something that changes every request, such as a timestamp or the user's newest message. The prefix hash differs each time, so the write premium is paid and no read ever occurs. Breakpoints belong on the last stable block.

Why it matters when choosing a harness

The harness decides what goes in the prefix, in what order, and where the markers go. Two harnesses on the same model can differ several-fold in cached share and in total tokens processed. Things to look for:

  • Static content first, dynamic content last; dates and file status injected into messages rather than the system prompt.
  • A tool list that stays fixed for the session. Adding one MCP tool mid-conversation invalidates the cached history, which is why Claude Code defers unused tools as lightweight stubs.
  • No model or reasoning-level switching mid-session; caches are per model.
  • Breakpoints anchored on the stable head (tools and system prompt) as well as the growing tail.
  • Cache read and write token counts exposed in usage output, so that it can be verified whether caching works.

Cache-hit percentage is a poor efficiency metric on its own. In one head-to-head benchmark OpenCode reached an 84.8% cache hit rate against Pi's 48.9% on the same task, yet Pi sent far fewer input tokens overall (about 27,000 versus 70,000 across a two-turn task), so its total cost was still lower. A large, stable boilerplate prompt inflates the hit rate without making anything cheaper. Uncached input tokens and dollars should be compared rather than percentages. That benchmark was a single community run on OpenAI-style automatic caching, so it is illustrative.

Caching and the harness of harnesses

The wrapper layer can help or hurt. A loop that restarts the agent with fresh context every iteration, as ralph-orchestrator does by design, pays a cold prefix on each pass unless the next iteration begins inside the cache lifetime and rebuilds the same prefix byte for byte. A fleet of N parallel agents on the same repository writes N separate cache entries unless they share an identical prefix. Hosted runtimes manage this but cannot be tuned. This is an inference from how the mechanism works, not a measured result, so cache read counts should be checked on real runs before it is relied upon.

Practical habits include keeping the prefix identical across runs (same tools, same order, same instructions), using the one-hour lifetime for work that pauses between steps, placing volatile content at the end, and logging cache read and write counts on every call.

The harness of harnesses

Once a harness can be driven programmatically, the next step is obvious: write something that starts it, watches it and restarts it. These tools do not replace Claude Code or Codex; they treat them as workers. They are grouped here by what they add.

1

Loop wrappers: keep one agent going until it is done

ralph-orchestrator is the clearest example. It implements the “Ralph Wiggum” technique: run the same agent again and again against a task until it reports completion or hits an iteration limit. It is a Rust tool (MIT) that wraps whichever CLI is already in use: Claude Code, Codex, Gemini CLI, Amp, Copilot CLI, OpenCode, Pi, Kiro and others. It adds hats (specialist personas that hand off through events), backpressure gates (tests, lint and type checks that reject unfinished work), persistent memories and tasks, and a Telegram channel for asking a human.

The design idea worth noting is backpressure: instead of trusting the agent's claim that it is finished, the wrapper makes the environment say no.

Also here: hand-rolled while true loops around claude -p or codex exec.
2

Parallel fleets: many agents, isolated worktrees

A human assigns several tasks; the tool gives each agent its own git worktree so they do not collide, then shows status and diffs for review. Three to ten agents is the range commonly reported as workable on one machine. The bottleneck moves from generating code to verifying it.

Examples: Claude Squad (MIT, Claude Code, Codex, Aider, Gemini), Conductor (proprietary, Claude and Codex), dmux (MIT, 11 backends), Vibe Kanban, amux, Kilo Code's Agent Manager. Cursor's Agents Window and /best-of-n are the same idea built into a harness.
3

Hierarchies: roles, supervisors and merge queues

Gas Town (MIT) models an engineering org: a Mayor coordinates, Polecats do the work, a Witness and Deacon watch for stuck agents, and a Refinery runs a merge queue. State lives in git-backed hooks and a structured issue tracker called Beads so work survives crashes. Heavier than a fleet manager, aimed at running many agents continuously.

Also here: Claude Code Agent Teams (experimental; teammates share a task list and message each other) and Factory's multi-Droid setup.
4

Hosted runtimes: hand over the sandbox too

The provider runs the harness, the sandbox and the session log. Work is assigned, and a pull request or result is returned later. This is where vendors are putting the most effort in 2026.

Examples: Claude Managed Agents, Claude Code on the web, Codex cloud, GitHub Copilot coding agent, Google Jules, Devin, Cursor cloud agents.
Why the layering matters. Each tier assumes the one below can be started non-interactively and observed. A harness with a headless mode, a stable protocol and readable session logs is easy to wrap; one that only works in a GUI is not. The process model matters too: a wrapper that spawns a CLI per task multiplies the footprint described above. This is a practical reason to check embeddability (axis 6) before a harness is standardised on.

Anthropic's agent products

Anthropic now sells several things that touch this stack at different levels, so it is worth separating them. “Anthropic's new Agents” is read here as the Managed Agents line, with the Agent SDK and Claude Code features beside it.

Harness

Claude Code

The reference harness. Recent additions include agent teammates (agent.spawn), a background “side agent” that monitors sessions, and mods: TypeScript functions that can rewrite prompts, add UI or replace built-in features (October 1, 2026).

Harness as library

Claude Agent SDK

Python and TypeScript. Runs the Claude Code loop by spawning the bundled CLI as a subprocess of the host application, with built-in file and shell tools, skills, sub-agents, MCP, session resume and permission controls. The loop, the sandbox and the session store are operated by the host’s own infrastructure.

Hosted harness of harnesses

Claude Managed Agents

A hosted REST API (public beta since April 8, 2026). An agent (model, prompt, tools, MCP, skills) and an environment (a configured cloud container) are defined, and sessions that exchange events are started. Anthropic runs the loop, sandbox and durable log. Reported pricing: standard token rates plus $0.08 per active session-hour.

Managed Agents also carries the features that look most like orchestration: outcomes (a separate grader agent checks work against a rubric and the agent iterates), multi-agent coordination (a lead delegates to specialists on a shared filesystem, auditable in the Console) and memory with a scheduled “dreaming” pass that curates it. Per the launch coverage, outcomes, multi-agent and memory were research-preview features needing separate access at the time of checking. Anthropic's stated guidance is to prototype locally with the Agent SDK and move to Managed Agents for production.

Compare this with ralph-orchestrator. Ralph wraps any CLI that is run locally and uses tests as the stop condition. Managed Agents wraps Anthropic's harness, hosts it, and uses a grader agent as the stop condition. Same shape, opposite trade: portability against convenience and lock-in.
