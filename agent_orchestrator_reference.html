A well-built agent orchestrator

A generalized specification for a local or self-hosted orchestrator that coordinates many AI agents on real work, with Octet as the worked example (Octet is coming soon). It states the principles, the architecture, the controls and a conformance checklist, and cites the standards and published practice each one rests on.

How to read the evidence. Claims tagged S · Sourced rest on a published specification or primary engineering post. Claims tagged P · Practitioner rest on practitioner or vendor write-ups and should be treated as good practice, not as a standard. Claims tagged O · Opinion are this document’s own design opinion. Several of the standards below are young. Where a spec’s status is unsettled, that is noted so you verify before depending on it.

Purpose and scope

An orchestrator turns a request into delegated work, runs that work through agents safely, and returns results a human can trust. It does not itself do the work. It owns five things:

  1. Decomposition: splitting a goal into units an agent can finish.
  2. Dispatch: giving each unit to an agent with exactly the context and authority it needs.
  3. Isolation: keeping concurrent work from colliding.
  4. Control: deciding what each agent may do, and who must approve what.
  5. Record: a durable, inspectable account of what happened and why.

Out of scope: the model itself, the editor, and the tools agents call. The orchestrator connects to these through open protocols (see Observability and standards).

Design principles

P1

Prefer code over model for control flow

Anthropic distinguishes workflows (LLMs and tools orchestrated through predefined code paths) from agents (LLMs dynamically directing their own process), and advises finding the simplest solution possible and adding complexity only when needed. S (Building effective agents) The 12-factor-agents methodology reaches the same place: most production agents are primarily deterministic software with LLM steps inserted at key decision points, not open-ended loops. P (12-Factor Agents)

Applied: the orchestrator’s state machine, scheduling and policy are ordinary code. Models are used for judgment inside steps.
P2

Orchestrator-workers fits unpredictable decomposition

A central model breaks a task down at runtime and delegates to workers; the surrounding control flow is still developer-written code. S P It suits multi-file code changes where the sub-steps cannot be known in advance.

P3

Give each agent its own small context

Subagents with separate context windows let work proceed in parallel without polluting one another, and the lead should persist its plan to memory because long runs can exceed the context window. S (How we built our multi-agent research system) 12-factor agents likewise names “own your context window” and “small, focused agents” as core factors. P

Applied: every worker starts fresh with a written assignment, not a shared transcript.
P4

Delegation briefs must be explicit

The multi-agent post found that the lead must write detailed, unambiguous task descriptions covering objective, output format, tools and task boundaries, and that agents misjudge how much effort a task deserves. S

Applied: a brief is a required, structured field, and the orchestrator scales effort rules (for example, one worker versus several) in code.
P5

Be honest about cost and fit

The same post reports multi-agent runs using roughly fifteen times the tokens of a chat interaction and being less effective for tightly interdependent tasks such as much coding work. S

Applied: parallelize only independent units, express dependencies explicitly, and cap concurrency.
P6

Enforce policy outside the model

Controls that live in code cannot be talked out of firing; controls that live in a prompt can. P (Arthur: human-in-the-loop governance)

Applied: permission checks, approvals and identity rules are deterministic, and a model may only summarize a pending decision for a human.
P7

Least privilege, per task

Both OWASP’s agentic risk list and NIST-linked guidance converge on task-bounded access, runtime policy checks and short-lived credentials over standing entitlements. P (OWASP Agentic Top 10 overview, CSA on NIST’s agent standards initiative)

Applied: each role gets only the tools and credentials its job needs, and only for as long as it needs them.
P8

Derive, don’t store, display state

Persist durable facts (what each agent last reported, what has merged) and compute labels like “needs input” at read time. O This prevents status from drifting out of sync with reality and makes recovery after a crash straightforward.

Roles

Separate roles by authority, not by prompt. A useful minimum set, and the one Octet, coming soon, uses:

RoleAuthorityWrites codeModel-driven
Intake (Chair)Creates goals, talks to the humanNoYes
Coordinator (Marshal)Decomposes, dispatches, merges approved unitsNoYes
Planner (Architect)Writes plans and specs onlyNoYes
Investigator (Scout)Read-only explorationNoYes
Builder (Engineer)Edits files inside one worktreeYesYes
ReviewerApproves or rejects unitsNoYes
Guard (Warden)Decides allow / deny / askNoNo, deterministic
Deliverer (Courier)The only role that leaves the machine (push, PR)NoYes, gated

The rule that makes this work: exactly one role can write, exactly one can merge, exactly one can leave the machine. Everything else is read-only. This is the least-privilege principle (P7) expressed as an org chart. O

Work model

  • Goal: one deliverable on its own branch.
  • Unit of work (bead): small enough for one builder and one reviewer to finish in a single pass.
  • Dependencies: explicit edges; a unit cannot start until everything it depends on has merged.
  • States: todo → running → in_review → (changes_requested ↺ running) → merged, plus failed. Transitions are enforced in code, and illegal ones (merging an unreviewed unit) are errors.
  • Branches: goal branch from the default branch; unit branch from the goal branch; units merge into the goal branch, and only the deliverer moves the goal branch off the machine.

Idempotency

Every state transition and every external side effect should be safe to repeat. Durable-execution systems record each step and skip completed ones on replay, but replay does not remove the need for application-level idempotency keys on external actions, and model calls made outside a step boundary are where re-spend happens. P (Durable execution for AI agents compared) A small event log plus a step wrapper on SQLite covers much of the need before adopting a workflow platform. P

Recommended. Start with the event log; adopt a durable-execution engine only when runs routinely outlive a daemon restart.

Isolation

  1. Filesystem: one git worktree per unit. No two agents share a working directory.
  2. Credentials: the child process environment is rebuilt per task. Inherited tokens and author variables from other identities are stripped, and only the project’s identity is injected.
  3. Network and remote: builders cannot push or open PRs. A guard compares a remote’s owner to the project’s account before any outbound action.
  4. Host: the orchestrator’s own API listens on loopback only, requires a per-session token, and rejects unexpected Host headers to defeat DNS rebinding. O
  5. Stronger sandboxing (containers or OS sandboxes for the builder process) is the next tier and is recommended when agents run with broad permission modes.

Security and governance

Threat model

OWASP’s Top 10 for Agentic Applications (published December 2025 by the OWASP GenAI Security Project) is the current reference list. P It is described here via secondary write-ups; read the primary document. Two entries matter most to an orchestrator:

  • Agent goal hijack: instructions injected into data an agent reads redirect its goal. NIST’s CAISI frames this as indirect prompt injection and recommends adaptive, repeated testing, with task-specific results examined alongside aggregates. P
  • Tool misuse and exploitation (ASI02): an agent uses a legitimate tool unsafely, through over-privileged tools, poisoned tool descriptions, or chains of tools whose combined effect nobody authorized. Mitigations: least-privilege tool scoping, treating tool descriptions as untrusted input, allowed-combination policies, and logging every call. P

Audit log

A governance reference lists what to record: model decisions, tool calls with arguments and responses, human approvals and overrides with reviewer identity, outputs, and system state such as agent and model versions; stored append-only with cryptographic integrity checks and restricted access. P (Governance best practices) Log before executing a risky action, since logging afterward documents an incident while logging before can stop it. P Hash-chain entries so tampering is detectable O, and where the stakes justify it keep a copy outside the agent’s host. Retention depends on your regulatory context; verify it against your own obligations.

Observability

Use OpenTelemetry’s GenAI semantic conventions so any backend can read your traces. S Status: Development. (GenAI agent spans)

  • invoke_agent {name}: one agent run, the root of a trace; a sub-agent’s run nests under its caller.
  • execute_tool {name}: one tool call, a child of the agent span.
  • Agent attributes include gen_ai.agent.name, gen_ai.agent.id and gen_ai.conversation.id; tool spans carry gen_ai.tool.name and a call id; token usage sits on the model-call spans.
  • Content capture is opt-in. Prompts, completions and tool arguments often contain sensitive data and should not be recorded by default.
Pin versions. These conventions were still marked “Development” as of mid-2026, so attribute names can change; isolate them behind one module. Beyond traces, track the orchestrator’s own health: queue depth, time in each state, approval wait time, rework rate (units sent back), and cost per goal.

Identity and multi-account work

Real users work across several accounts. The orchestrator must make the wrong account impossible, not just unlikely. O

  1. No default identity. A project without an explicit identity cannot start work.
  2. Identity profile = author name and email, one SSH key, and one forge login. Applied through environment variables on every child process, never through the user’s global git config.
  3. IdentitiesOnly. Force the SSH client to offer only the project’s key, otherwise an agent can silently present the wrong one.
  4. Remote ownership guard. Before starting work and before any push, the remote’s owner must match the identity’s user or an explicitly listed organization.
  5. Credentials stay with the deliverer. Builders hold no forge credentials.
  6. Verify on demand. A doctor command checks each key and token against the forge.
