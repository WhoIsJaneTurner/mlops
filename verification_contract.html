The verification contract

A short, written statement of what is guaranteed to be checked before a change merges, and what only could be checked if someone remembers to. The methodology grew organically out of everyday practice and is a synthesis of current guidance from Google, Microsoft and GitHub on verifying code that coding agents write. It is offered as a proposition: an attempt at what could work.

What the contract is

This is not about testing in general. It is about one thing: making it explicit, in writing, what is actually guaranteed to be checked before a change merges, versus what merely could be checked if someone remembers to.

Most repositories have tests. Few have a contract: a short, named, discoverable statement of exactly which parts of the system are protected, by what, and how firmly. Without one, “we have tests for that” quietly becomes “someone wrote a test for that once”, and nobody can tell the difference until a bug gets through.

No change to a guarded surface merges without its corresponding check passing. Where that check is not automated, the pull request must show the check’s output, not just assert correctness.That is the whole contract. The rest of this article is how to put it in place.

Why it matters more with coding agents

When a person writes and reviews every line, the contract can live in their head. As agents take over the writing, people stop reading every diff, and the published guidance from Google and Microsoft converges on the same conclusion: generating code is no longer the hard part, verifying it is. Sourced A verification contract is a small, concrete way to make that verification explicit, so that it can be enforced by CI, by a reviewer, or by an orchestrator that runs many agents.

Why now: verification is the bottleneck

The eight levels of AI-assisted coding

Steve Yegge’s informal eight-level model, described in early 2026, runs from no AI (level 1), through an agent in the editor with approvals on (2) and off (3), watching the agent instead of its diffs (4), working from the terminal and checking code later (5), running several agents in parallel (6), and managing ten or more by hand (7), to building an orchestrator that coordinates a fleet of agents (8). Sourced

Commentary on the model describes how review changes along the way. At level 7, reviewers face parallel streams of pull requests and review tends to become rubber-stamping. At level 8, the developer’s work shifts to stating intent, decomposing work and designing where human judgment is required, verification moves into an automated pipeline, and verification replaces generation as the bottleneck. Sourced The model is a practitioner’s framing, not a standard; neither Google nor Microsoft uses it.

What Google expects

Google’s whitepaper The New SDLC With Vibe Coding (Osmani, Saboo and Kartakis, May 2026) is the most direct statement. Sourced

  • Verification is the dividing line. “The single biggest differentiator between the two ends is how outputs get verified.” Without both tests and evaluations, the practice is still vibe coding.
  • Rigour scales with risk. Disposable code may rely on little checking; structured AI-assisted work needs human judgment at key checkpoints; production systems need “systematic verification at every stage”.
  • Check how, not only what. Output evaluation checks the final result and trajectory evaluation checks the sequence of tool calls and reasoning. “A fluent output that skipped its verification steps is a more dangerous failure than one with a visible error.”
  • People stay accountable. “AI-generated code requires the same or greater scrutiny than human-written code,” and “Review every line the agent produces that is going to ship.” AI review supplements human review.
  • The agent’s configuration is production code. Rules files, prompts and evaluation suites are version-controlled, changed by pull request and owned. “Hooks are the place for things the agent should never forget but often does.”

Google’s DORA research adds the delivery picture. The 2025 State of AI-assisted Software Development report finds that AI adoption now improves throughput but still increases delivery instability, and its foreword mentions failures including “silently deleted tests”. Sourced Two of the seven capabilities in DORA’s AI Capabilities Model bear directly on verification: strong version control (“your critical safety net”) and working in small batches, because large AI-generated blocks “are hard to review and test”. Sourced

What Microsoft and GitHub expect

GitHub’s responsible-use documentation for the Copilot cloud agent puts the burden on the user (“You should review all outputs generated by the agent thoroughly prior to merging”) and builds controls into the platform: the agent cannot push to the default branch, workflows triggered by its pull requests need approval from someone with write access, commits are co-attributed to the person who started the session and link to session logs, and automated security checks do not replace human review. Sourced

Microsoft’s February 2026 update to its Security Development Lifecycle extends it to AI with threat modelling for AI workflows, agent identity and access control, and observability, and concedes that “evolving agent behaviors outpace traditional review processes”. Sourced Microsoft’s 2025 Agentic DevOps post describes agents working “with your guidance and approval”, though one example has an operations agent deploying a fix before people were told, a looser bar than Google’s. Sourced

The contract in six steps

1

Identify your guarded surfaces Practice

A guarded surface is any part of the system where a bug would be:

  • silent: wrong output, no error, no obvious symptom; and/or
  • expensive or hard to reverse once it ships: reprocessing a full dataset, a wrong value spreading into every downstream join, a corrupted identifier that cannot be told apart from a correct one by inspection.

Not everything qualifies. Keep it to a short, named list; if everything is “guarded”, the word means nothing. Typical examples are an identifier-minting or hashing rule, a pricing calculation, a schema migration, an authorisation check, or a serialisation format that two services both depend on.

Scaling scrutiny to stakes is the same idea as the risk tiers in Responsible agent deployment and evaluation, applied to code instead of agent behaviour.

Include the checking apparatus and the boundaries. The graders, scorers, CI test discovery and evidence files that report on everything else belong on the list too; in practice they are where many silent failures live. So do the boundaries between components, which no per-component check covers. Field (see Field lessons)

2

Write one check per surface Practice

Each guarded surface gets exactly one thing that can answer “does this still hold?”: a script, an assertion harness, a property test or a golden-file diff. It need not be elaborate. It needs to be:

  • Runnable on demand, independently of the full test suite.
  • Named after the surface it guards, not after whatever produced it, so the next person, or agent, finds it by thinking about the surface rather than the history.
  • Able to fail loudly on the exact corruption it exists to catch. A check that cannot be made to fail by deliberately breaking the thing it guards is not a check.
  • Real where it matters. A guarded check must not mock the surface it guards. Stand-ins for things around it are fine; a stand-in for the thing itself turns the check into a test of the stand-in. Proposed
  • Controlled in both directions. Give the check a known-bad input it must flag and a known-good input it must pass. When proving it can fail, break the code path it guards, not a constant or helper the check also reads, or both sides move together and the check stays green. Field

For the highest-stakes surfaces, one check may not be enough: an error that shows in one place but not another needs a second, independent check that observes through a different channel. Field (see Field lessons)

Prefer data-driven checks. Where possible, keep the cases in data rather than in code: a table or file of inputs and expected outputs that the check iterates over, drawn from samples of real records, the specification and known past failures. Practice Data-driven cases are easy to extend without touching the check’s logic, easy for a reviewer to read, and make it obvious when a case was removed. They also double as the specification an agent works to. Two conditions keep them honest:

  • Expected values need an independent source: the specification, a hand calculation, a reference implementation or a previously verified release. Values copied from the current output of the code under test only prove the code agrees with itself.
  • The data should change. Refresh samples from real data on a schedule, and add every escaped bug as a new row. Property-based tests, which generate inputs, are the natural complement for pure logic.

Watch for baked-in responses

A baked-in response is an answer hard-coded somewhere, in the code, a mock, a fixture or an expected-value file, that lets a check pass without the real logic running. Agents produce them readily when asked to make a failing test pass, and they are easy to miss in a large diff. Treat them as a standing review question, not a one-off. Proposed Signs to look for:

  • Code that special-cases test inputs (if customer_id == "TEST-001") or returns a constant on the path the tests exercise.
  • A mock or stub set up to return exactly the value the assertion checks, so the test is true by construction.
  • Expected values or snapshots regenerated from current output and accepted without review.
  • Recorded responses with no date or refresh, so the real dependency has moved on and the recording has not.
  • Error handling that swallows a failure and returns a default that happens to satisfy the test.
  • A summary quoting test output that no recorded run produced.

Defences: break the real surface on purpose and confirm the check fails; vary the data so a hard-coded answer stops matching; and treat any change to a guarded check’s mocks, fixtures, recordings or expected values as a change to the guarded surface itself, with the same evidence required.

3

Classify each check, how firm and how real, and say so out loud Practice

This is the step most projects skip, and the one that matters most.

  • Automated (CI-enforced): runs on every pull request without anyone deciding to run it. It cannot be forgotten, only disabled, and disabling it is a visible, reviewable act. With branch protection and required status checks, it also binds agents that never read the guidance.
  • Manual (convention-enforced): needs real data, a VPN, an expensive fixture or another precondition that keeps it out of CI. It is real verification, but only as strong as the discipline of whoever is supposed to run it.

Both are legitimate. The failure is not having a manual half; it is not labelling it as manual, so it is treated with the confidence of the automated half. Write both lists side by side in the same document.

Two refinements from practice. Field First, a check has three outcomes, not two: a check that errored, was skipped or inspected nothing is inconclusive, and must never be counted as a pass or averaged in. Discovering zero tests, or reading zero files, should fail the job. Second, “automated” should say where and when the check runs; CI that triggers only on a branch nobody works on is not enforcement.

Firmness is one label. The second is fidelity: how close the check runs to the real thing. Proposed

  • DirectPure logic with nothing external to stand in for: the real code on real or generated inputs. Property tests and golden files live here, and they are fast enough for CI.
  • LiveRuns against the real dependency or environment. Highest fidelity; often manual, because it needs access, data or cost that CI does not have.
  • Snapshot or containerA copy of the real thing: a production-schema snapshot, a containerised service, a sampled dataset. Usually the best route for moving a live check into CI without losing much fidelity.
  • RecordedReplays responses captured from the real dependency. Acceptable with a capture date and a refresh schedule; stale recordings are a common source of baked-in responses.
  • MockedA hand-written stand-in. Fine for what surrounds the surface, never for the surface itself.

The two labels explain each other. High-fidelity checks tend to be manual because they need real data or access; the usual way to automate them is to move from live to snapshot or container, not from live to mocked. Many of the silent, irreversible bugs the contract targets sit at boundaries such as schemas, data shapes and formats another service reads, which is why guarded checks often look more like integration tests than unit tests. For a format shared between services, consumer-driven contract testing (Pact and similar tools, unrelated to this article’s use of “contract”) is one well-established way to check it.

4

Enforce the manual half at review, not just when writing Practice

A manual check that only the author is trusted to run is weaker than it looks. Code review closes the gap: a reviewer who approves a change to a guarded surface asks for the check’s output, and does not accept a claim of correctness in the description.

A common way this fails: an automated review pipeline (static lint, structural grounding, documentation drift, pattern search) approves a rewrite of guarded logic without any phase running the script written to test that logic, because none of the phases execute code. The script already exists; what is missing is a rule that reviewers, human or automated, treat “guarded logic changed and a matching check exists” as a trigger to run it, not to read about it.

If your review process, human, bot or both, only reads diffs and text, it cannot verify that a manual check happened. Say that limitation out loud too.

Evidence, strongest first. With agents in the loop, pasted output is weaker than it used to be: an agent can produce text that looks like a passing run. Prefer evidence the reviewer can trace or reproduce. Proposed

  • CI resultThe check ran in CI on the head commit and is a required status. Nothing to argue about.
  • ReproducedThe reviewer, or a reviewing agent with the needed access, ran the check on the head commit and got the same result.
  • TraceableOutput attached with the exact command, commit SHA and time, linked to the session log or run record that produced it.
  • PastedOutput pasted into the description with no trace. Acceptable for low-stakes surfaces only.
  • Claim“Verified locally”, “tests pass”. Not accepted for a guarded surface.

The same logic applies to agents themselves: regression suites that should stay near 100% are the agent-side equivalent of a check that must pass. See Testing in the responsible agent framework.

5

Name your excluded zone Practice

Every contract has a boundary, and the boundary should be a stated fact, not a gap discovered by surprise. If a check is known to be broken, not yet written, or structurally blocked from running (for example, CI cannot give every test its own isolated data root), write it next to the contract: “X is not currently covered, here is why, here is what would need to change.” An undocumented gap looks identical to a covered surface until it fails. A documented one is a known risk someone can prioritise.

6

Put the contract where the work happens Practice

A contract that lives only in a conversation, a wiki page nobody opens during a pull request, or someone’s memory is not a contract; it is a story about one. Put it:

  • Inline in the repository’s agent and contributor guidance (AGENTS.md, CLAUDE.md, CONTRIBUTING.md) as a short, named block: one sentence stating the rule and a pointer to the full table. This is where coding agents read their instructions, so it is where they learn which surfaces are guarded.
  • Next to the tests (a testing/README.md or equivalent), with the automated and manual split as an actual table, not prose buried in a longer document.
  • In the pull request template or review checklist, so “did you run the check for the surface you touched?” is a question that gets asked, not assumed.

Treat the contract like the rest of the agent’s configuration: version-controlled, changed by pull request, with a named owner. Sourced

Back every rule with a test or guard. A rule in the guidance file states intent; it does not enforce it. A rule written down, even with the incident behind it named, can leave the code it prohibits in place. Field (see Field lessons)

Applying it to a new project

  1. List the three to six places where a silent or irreversible bug would hurt most. Resist listing more; a long list pulls attention away from the surfaces that matter.
  2. For each, confirm a check exists or write one. Make it fail on purpose once, to prove it can.
  3. Sort each check into automated or manual. Wire every automated one into CI as a required status now, not eventually.
  4. Write the one-sentence contract and the table (surface, check, enforcement) into a document the team, and its agents, will actually open.
  5. Add the excluded-zone list, even if it is short, even if it is embarrassing.
  6. Revisit the table whenever a check moves between columns. A manual check graduating into CI, or a CI check quietly skipping, are both contract changes worth a one-line note.

The point is narrow: “we test for that” becomes a claim anyone on the team can verify by reading one table, instead of a claim only the person who wrote the test can vouch for.

Field lessons

  
Where these come from. These lessons come from the site owner’s hands-on work on a software project built largely by coding agents. The project’s purpose and details are confidential and are not described here. Every lesson has been generalised, and the examples are invented to show the mechanism; they are not accounts of what happened. Lessons on this tab are tagged Field.

  

  
Two patterns ran through nearly all of it. First, the most costly defects were not in the product logic but in the checks: the graders, scorers, test doubles and CI configuration that reported success they had not earned. Second, almost every error in those checks made results look better than they were. Errors that make results look worse get investigated because they get in someone’s way; errors that flatter tend to be believed. Good news deserves extra scrutiny.

  


  
The checks are surfaces too

  
Every checker needs controls in both directionsFieldSteps 1–2
    
Lesson. A check that grades other code needs a known-bad input it must flag and a known-good input it must pass, run before any of its results are trusted.

    
What went wrong. Checkers were built that could not fire at all: one ignored the observations it had just collected when deciding its verdict; another looked for a pattern the real inputs never use. Their clean results looked like real passes. A later checker failed in both directions across two versions, first raising false alarms, then missing a real defect.

    
What worked. A self-check mode that runs the checker over deliberately broken copies and requires it to flag each one; paired “everything present” and “nothing present” synthetic inputs; a deliberately wrong reference implementation as a source of guaranteed failures. Controls can be wrong too. A control that lacks the property it claims, or fires for the wrong reason (matching an unrelated substring, say), proves nothing, so the controls need checking as well.

  

  
“Could not check” is an outcome, never a passFieldSteps 2–3
    
Lesson. A check that errored, was skipped or inspected nothing must report itself as inconclusive or failed. It must never fold into a pass, a zero or an average.

    
What went wrong. Broad exception handlers turned outages into empty results that read as clean. A policy gate passed after reading none of the files it was meant to inspect. Test discovery silently skipped whole directories. Integration tests that could not find their fixtures returned early and counted as passes. A script run from the wrong directory reported success on zero files. A missing number defaulted to zero and quietly satisfied a rule.

    
What worked. Failing closed: discovering zero items, or running zero suites, fails the job. Parsers raise on input they cannot read instead of skipping it. Missing values are stored as null, never zero. Every skip names its cause, and the skip count is reported beside the pass count.

  

  
Prove a check can fail by breaking the wiring, not a shared valueFieldStep 2
    
Lesson. To prove a test can fail, corrupt the code path it guards. Do not change a constant or helper that both the test and the code read: both sides move together and the test stays green.

    
What went wrong. Converting hard-coded expectations into ones derived from shared configuration created tautologies, and a “proof of failure” that edited the shared value left the test passing. Elsewhere, an “independent” checker shared a defect with the code under test, so both agreed on the wrong answer, and one expected value had been computed from the implementation’s own output.

    
What worked. Recorded fail-then-revert proofs: the deliberate corruption, the exact failing assertion, evidence the corruption was reverted, and which cases still passed in both states, labelled as controls. A third, independent implementation to settle disagreements between code and checker. The rule: inputs may be pinned, but expectations must come from something the code under test does not control.

  

  
Each assertion must tell the two states apartFieldStep 2
    
Lesson. For every assertion, name the broken state it rules out, and confirm it gives a different result in the working and the broken state.

    
What went wrong. Suites passed against code that did nothing. A UI test asserted a label shown in every state. A mock returned the same response for every argument. A fixture’s values made a transformation a no-op, so code that never applied it still passed. Success flags were set unconditionally. A status assertion accepted every plausible code. An error-path test checked only that the call returned.

    
What worked. Mutation by deletion: copy the module aside, delete the behaviour under test, and confirm the suite goes red. Fixtures chosen so the operation under test actually changes the values. Assertions on structure rather than strings. A standing review question: does anything in the code express the intent this test checks?

  


  
Stand-ins and fidelity

  
No mock path in shipped code; a guidance rule alone does not remove oneFieldSteps 3, 6
    
Lesson. If production code can return canned answers when a dependency is missing or a mode flag is unset, some check will eventually pass on the canned answer. Remove the path or make it fail loudly, and guard the removal with a test.

    
What went wrong. The original brief to the agents asked for a switch between mock and real modes. The agents built a deterministic mock tier and made it the default. A validator approved every input; a client returned a hard-coded object without making a network call; a verifier treated any successful HTTP response as success; a fixture value was later quoted as if it were a measurement; and CI was configured to pass against the mock tier. A rule against mock modes was then added to the agent guidance, and a later audit still found the violating default in code.

    
What worked. Deleting mock modes outright, so a missing dependency returns an explicit “unavailable” error; feeding known-bad inputs to validators; running checks against a real service or container.

  

  
For the highest-stakes surface, one check is not enoughFieldStep 2
    
Lesson. Where an error can show up in one place but not another (a stored value, an API response, what is displayed), use at least two checks that share no code and observe through different channels, and run them on real inputs as well as fixtures.

    
What went wrong. A component reached a perfect score on hand-built fixtures and was reported fixed. Running the same check on a sample of real inputs found many failures from ordinary variations no fixture contained. Another class of failure was invisible to that check at any sample size; only a second check observing a different channel could see it.

    
Invented illustration. A price is correct in the API response but rendered wrongly on screen. A check that reads the API cannot see the rendering bug, however many records it reads. Sample width and observation channel are separate axes; widening one does not cover the other.

    
What worked. Two independent checks on different channels, plus a sweep over real inputs. Each check reports the cases it cannot judge separately rather than scoring them. The real-input sweep stayed manual because the inputs could not be stored in CI, so each defect it found was reduced to a synthetic regression case that could run there.

  

  
Verify the artifact that ships, where it runsFieldStep 3
    
Lesson. Build each deployable unit in isolation, confirm the artifact under test is the one just built, and run browser code in a real browser.

    
What went wrong. Building each service from only its own directory revealed packaging defects in most of them, including an image that could never have started. A shared workspace had hidden undeclared dependencies. Code compiled and then failed when loaded. Tests passed in a simulated browser and threw in a real one. A measurement run silently used a stale build. Configuration repeated across files drifted until a cross-file consistency check was added, which immediately found more. A build recorded as fixed was broken by a test added later, and nobody rebuilt.

    
What worked. An isolated-build gate per component; artifact hashes recorded with results; tooling that rejects stale or incomplete run records; real-browser runs with an independent check of what was displayed; automated cross-file consistency checks; a rule to re-run a check whenever its subject changes.

  

  
Test against the real neighbourFieldStep 1
    
Lesson. Per-component checks do not cover the contracts between components. Run at least one consumer against a live instance of each provider.

    
What went wrong. Every component passed its own gates. Defects appeared only when one agent’s component ran against another’s live service: mismatched paths and request shapes, required parameters accepted but never read, options dropped in transit, a container missing data its own evidence file said it had, and a reader ignoring part of the provider’s output. Client-side test doubles had encoded an endpoint shape the real server never used.

    
What worked. Consumer-driven runs against real containers as part of each consumer’s admission gate.

  


  
Evidence and review

  
Keep the evidence, and make it reproducibleFieldStep 4
    
Lesson. Every reported number needs its raw output stored beside the tool that produced it, and a command that reproduces it. Summaries should be recomputed from the raw rows.

    
What went wrong. Raw outputs lived in an ignored working directory and survived only as numbers typed into prose; some cited files did not exist. An evidence folder kept at a relative path was lost, and the figures that depended on it could no longer be reproduced. A summary statistic reported a change between two byte-identical runs. A derived reliability figure inverted its own formula. A test “guarded” a key figure by checking that the number appeared in a note.

    
What worked. Committing raw outputs; a “Reproducing” section with commands in every findings document; recomputing statistics from saved rows; property assertions on derived formulas (a value that must rise when its input rises); running twice and requiring a match before reporting any difference.

  

  
Label every figure with how it was obtainedFieldSteps 3–4
    
Lesson. Tag each recorded value as measured, human-scored, asserted, inferred or unrecorded, and default the tag to “asserted” so an untagged value cannot pass as measured.

    
What went wrong. Hand-typed coverage figures, agent-invented effort estimates, hard-coded verdict tables in scoring code and counts padded with items that did not qualify all looked measured. A scorer labelled its evidence “real” while running nothing. A figure flagged as unreliable kept being reused until it was removed: disclosure is not correction. The same status fact, maintained by hand in several places, drifted apart.

    
What worked. A per-record source field defaulting to “asserted”; re-deriving every row of a scored table against code and tests; deriving verdicts from runtime behaviour instead of tables; one evidence file per component instead of central status files; marking anything unmeasured as inferred or unrecorded rather than estimating it.

  

  
A component’s report about itself is not evidenceFieldStep 2
    
Lesson. Self-reported confidence, success flags and supplier metadata must be checked against independent ground truth, never asserted on as stand-ins for correctness.

    
What went wrong. A model-based component reported uniformly high confidence on output with obvious errors, and a test asserted on that confidence. Success flags reported work that had not happened. A “verified” field came from a component grading its own output. Supplier metadata about test inputs was wrong. A mean error rate hid one extreme outlier.

    
What worked. Error rates measured against ground truth known when the test input was generated, with a deliberately wrong “truth” as a control that must fail; reporting the range as well as the mean.

  

  
Review the whole change, and prefer reproduction to readingFieldStep 4
    
Lesson. Per-task review misses defects that span tasks, and a review that reads code without running it is one reader’s opinion. Add a whole-change review that runs edge-case and malformed inputs, and grade each finding by whether it was reproduced.

    
What went wrong. Whole-change reviews repeatedly found serious defects that no per-task review could see, such as a cleanup step that deleted real content, an environment incompatibility and a race condition. An early multi-agent review that read code and ran unit tests certified figures that were later overturned, one of them a mock value. A later large read-only audit found real issues quickly, but by its own account most findings were code reading, and some of its premises were wrong. A plain question from the human, “does this actually work?”, surfaced several defects in a component with an extensive passing suite.

    
What worked. A mandatory final whole-change review, one bounded round of fixes, and an independent re-review that reproduces each fix; mutation proofs attached to audit findings.

The adjustments below are proposed from the lessons above. Proposed

  

    
StepAdjustment

    
      
1. Guarded surfacesList the verification apparatus itself (graders, scorers, CI test discovery, evidence files) among the guarded surfaces. Add the boundaries between components as surfaces, checked by running a consumer against a live provider.

      
2. One check per surfaceOne primary check per surface, but the highest-stakes surfaces get at least two independent checks that observe through different channels, plus a run over real inputs. Every checker gets a must-fire and a must-not-fire control. Prove failure by breaking the wiring; take expectations from something the code does not control; make every assertion tell the working and broken states apart.

      
3. Firmness and fidelityAdd a third outcome, inconclusive, that is never counted as a pass or averaged in. Record where and when a check runs, not only whether it is automated: CI that runs only on a branch nobody works on is not enforcement. Treat a shared, unisolated environment as a loss of fidelity.

      
4. Evidence at reviewEvidence must persist: raw output stored, a command to reproduce it, a date, and a trigger for re-running it. Tag figures by how they were obtained, defaulting to “asserted”. Recompute summaries from raw rows. Review the whole change, and grade review findings by whether they were reproduced. Give good news extra scrutiny.

      
5. Excluded zonePin the list with a test that names every entry; agent edits can silently drop entries, and a count-only test shows that something went but not what. Declining to build a check that cannot be shown to fire, and naming the gap, is a legitimate outcome. Treat claims such as “not supported” or “large effort” as checks to run, not answers. State the sample size behind any reliability claim; zero failures in a small sample supports only a modest bound (see Calibration in the responsible agent framework).

      
6. Where the contract livesBack every guidance rule with a test or guard; a rule written down, even with its originating incident named, did not remove the code it prohibited. Word briefs carefully: asking agents for a mock switch produced a mock default.

    
  


  
Working with agents

  
    
    
  • Ask for a stand-in and it becomes the default. A brief that asked for a mock/real switch produced a mock tier as the default path, with CI tuned to pass on it.
    • 
    
  • Claims ran ahead of evidence. Commit messages and summaries described fixes and behaviours the code did not yet have.
    • 
    
  • Agents’ own checking scripts were wrong at a steady rate: sweeps that skipped branches, counters that dropped items, scripts that passed on zero files. This happened even shortly after the same agent had diagnosed the same class of flaw elsewhere. Knowing the failure mode did not prevent it when the check and the expectation came from the same place.
    • 
    
  • Agents fitted the product to a broken fixture. When a control fixture was wrong, the first agent fix changed the product logic to match it.
    • 
    
  • Agents trusted their briefs. Wrong premises in a brief were caught only once agents were told to verify premises before acting.
    • 
    
  • Bulk edits silently dropped content from structured lists, and code was classified by the folder it sat in rather than by what referenced it.
    • 
    
  • Agents sharing one environment corrupted each other’s results. Contradictory test counts from parallel runs were nearly recorded as product defects.
    • 
    
  • Self-checks stayed inside the agent’s current frame. Most corrections came from the human declining that frame, or from evidence outside the agent’s context: the original requirements, the actual dates, a plain question.
    • 
    
  • Read the test, not the summary of it. Confirming a regression test meant reading the test itself, not accepting an agent’s description of it.
    • 
    
  • What worked: a four-gate admission sequence per component, written into the agent guidance with the incident behind each rule. The component is self-contained; it builds in isolation; its own tests pass, with skips counted; and its output is checked by an independent tool. The evidence lives in a file beside the component.
    •
